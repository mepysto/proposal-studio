## 1. 시작과 권한

기본 관리자 계정은 없습니다. 설치 과정에서 최초 관리자를 만들고 이후 관리자가 사용자 계정을 발급합니다.
업무 담당자 이름과 실제 계정 역할은 다를 수 있습니다. 버튼이 보여도 서버 권한에 따라 요청이 거부될 수 있습니다.

| 작업 | 서버 권한 기준 |
|---|---|
| 대시보드·지도·본인 조직 현장 조회 | 로그인 사용자 |
| 현장·장비 등록/수정/삭제 | `admin` 역할 또는 슈퍼유저 |
| 녹화 시작·중지, 적설 이벤트 관리 | `admin`, `operator` 또는 슈퍼유저 |
| 경보 확인·할당·해결, 피드백·일지 작성/수정 | `admin`, `operator`, `maintenance` 또는 슈퍼유저 |
| 일지 삭제 | `admin` 또는 슈퍼유저 |
| 수동 히터 제어·Control Logs·명령 원장, 사용자·모델 관리, 전력 예측 | 슈퍼유저 |
| 서버 공통 설정 변경 | `admin` 역할 또는 슈퍼유저 |

`admin` 역할만 가진 계정과 `is_superuser` 계정은 다릅니다. 조직 밖 현장·장비·구역은 조회가 제한됩니다.
가열 구역 생성·수정 등 상세 권한은 API 계약을 기준으로 합니다.

설치 담당자는 `central/docs/DEPLOYMENT_GUIDE.md`, 현장 담당자는
`edge/docs/06_Jetson_Orin_Nano_Deployment.md`를 따릅니다.

## 2. 공통 화면과 로그인

![로그인](screenshots/01_login.png)

1. 웹 주소의 `/login`에 접속합니다.
2. 이메일과 비밀번호를 입력해 로그인합니다.
3. 대시보드가 표시되는지 확인합니다.
4. 업무 종료 시 상단 사용자 메뉴에서 로그아웃합니다.

기본 설정에서 비밀번호를 5회 연속 틀리면 15분 잠깁니다.
브라우저 세션은 서버 요청으로 갱신되며, 토큰 유효시간 기본 30분·최대 로그인 유지 기본 12시간입니다.
대시보드 자동 조회도 요청에 포함되므로 마우스·키보드 미사용 시간과 정확히 같지는 않습니다.
비밀번호 변경·로그아웃 등으로 기존 세션이 폐기될 수 있습니다.

왼쪽 메뉴는 대시보드, AI 관제, NOC, GIS 지도, 현장 관리, 운영일지, 매뉴얼, 설정입니다.
상단에서 언어·경보·프로필을 확인합니다. 작은 화면에서는 메뉴 버튼으로 사이드바를 엽니다.
운영체제의 ‘움직임 줄이기’를 지원하며 상태는 색상과 글자를 함께 사용합니다.

## 3. 대시보드와 경보

![대시보드](screenshots/02_dashboard.png)

대시보드 `/`는 현장 수·상태, 노면 상태, 전력, 장비, 날씨, CCTV 스냅샷, 최근 경보를 보여줍니다.

1. 도시 필터와 검색으로 담당 현장을 찾습니다.
2. 최근 경보에서 위험도 높은 항목을 먼저 확인합니다.
3. 현장 카드나 경보를 눌러 현장 상세로 이동합니다.
4. 센서·기상·Vision 갱신 시각과 CCTV를 함께 대조합니다.
5. 경보 처리 결과는 NOC와 운영일지에 남깁니다.

![경보 예시](screenshots/14_notifications_alerts.png)

상단 경보 벨과 팝업에서도 최근 경보를 확인할 수 있습니다.
새 경보는 SSE와 주기 조회로 갱신됩니다. 연결이 끊겼다면 새로 조회해 현재 목록을 확인합니다.
KPI의 0 또는 빈 목록은 데이터가 없을 때도 나타날 수 있으므로 ‘정상 측정’으로 단정하지 않습니다.

## 4. AI 관제

![AI 관제](screenshots/03_ai_overview.png)

`/ai`에서 현장을 선택한 뒤 다음 항목을 확인합니다.

| 항목 | 확인할 내용 |
|---|---|
| KPI·위험도 | 적설·결빙 위험, 요구 열량, 지연, 피드백·엣지 상태 |
| 예열 타임라인 | 강설 예상 시각, 예열 시작까지 남은 시간·예상 소요 |
| XAI 설명 | 어떤 관측·위험 요인이 판단에 반영됐는지 |
| 이벤트 | 적설·융설 이벤트, 저장된 성공률·절감량, PDF |
| 제어 결정 | 단계, 이유, 지연, 피드백 |
| 예보 | 온도·습도·풍속·강설·강수 확률과 출처·시각 |
| 모델 | 권한이 허용한 모델·버전·배포 단계 |
| 피드백 | 판단에 대한 운영자 라벨 |
| 엣지 | heartbeat·온라인 상태·전송 적체 |

![ESG·예열 예시](screenshots/13_ai_active_and_esg.png)

점검 순서:

1. 현장을 선택하고 위험도·예보·관측 시각을 확인합니다.
2. 제어 결정의 사유와 현장 CCTV·센서를 비교합니다.
3. 부정확한 판단에는 피드백을 남깁니다. 피드백 저장이 모델을 즉시 재학습시키지는 않습니다.
4. 이벤트 보고가 필요하면 PDF를 내려받습니다.
5. ESG 값은 저장된 이벤트 절감량의 환산치로 해석합니다. 공인 절감 실적은 별도 검증이 필요합니다.

모델을 registry에서 승인해도 실제 worker의 모델 파일은 자동 교체되지 않습니다.
모델 관리·성능 평가는 전문 담당자가 AI 기술 명세를 따릅니다.

## 5. GIS 지도와 가열 구역

![지도](screenshots/05_map.png)

`/map`에서 2D(Leaflet)·3D(Cesium)를 전환하고 도시·현장을 선택합니다.
마커·billboard의 현장 팝업에서 현장 상세로 이동할 수 있습니다.
3D 지도는 장비·열지도·미니맵·구역 편집·시간 탐색을 지원합니다.
날씨 효과는 화면 시각화이며 실제 기상 관측을 대신하지 않습니다.

열지도는 구역의 온도 샘플을 공간 보간한 결과입니다. 미래 시각은 예측이므로 현재 실측과 구분합니다.
위치가 없거나 외부 지도 리소스에 접속할 수 없으면 지도가 비거나 일부 요소가 보이지 않을 수 있습니다.

![가열 구역 편집](screenshots/04_ai_zone_editor.png)

가열 구역 편집:

1. AI 관제의 가온 구역 편집 또는 지도 편집 화면에서 대상 현장을 확인합니다.
2. 실제 가열 영역을 따라 꼭짓점을 순서대로 지정합니다.
3. 최소 3개 점과 구역 정보·좌표·면적을 확인합니다.
4. 잘못 그렸으면 초기화한 후 다시 지정합니다.
5. 완료·저장 후 구역 목록에 반영됐는지 확인합니다.
6. 각 히터를 해당 구역에 연결하고 Edge의 구역·장치 ID도 맞춥니다.

GIS 위경도 구역과 CCTV 픽셀 ROI는 다릅니다. 구역을 그렸다고 카메라 분석 영역이 자동 갱신되는 것은 아닙니다.

## 6. 현장·장비 관리

![현장 목록](screenshots/06_sites_list.png)

현장 관리 `/sites`에서는 검색·도시 필터·페이지 이동으로 현장을 찾습니다.
권한이 있으면 현장 추가에서 이름·주소·좌표·담당자 등을 입력합니다.
저장 후 목록과 지도에서 위치를 확인합니다.

![현장 추가](screenshots/07_site_add_modal.png)

현장 상세 상단에서 메타데이터를 수정할 수 있습니다. 삭제 전에는 운영 이력·연결 장비 영향을 확인합니다.

![장비 구성](screenshots/09_site_detail_devices.png)

장비 등록·수정:

1. 현장 상세 → 장비 및 구성으로 이동합니다.
2. 장비 추가 또는 기존 장비 수정을 선택합니다.
3. 카메라·센서·전력 장비 유형, IP·RTSP·설정을 입력합니다.
4. 히터는 가열 구역을 선택합니다.
5. 저장 후 실제 수집·영상·명령 전달이 정상인지 확인합니다.

| 히터 구역 표시 | 의미·조치 |
|---|---|
| 구역명 `#ID` | 명시적으로 연결됨 |
| 자동: 구역명 | 현장에 단일 구역이 있어 자동 연결. 구역을 추가하면 직접 지정 필요 |
| 미지정 | 여러 구역 중 하나를 지정해야 함 |
| 가열 구역 없음 | 구역을 먼저 생성 |
| 다른 현장의 구역 | 현재 현장의 구역으로 수정 |

구역이 불명확한 히터는 중앙이 명령을 보내지 않고 경보 처리합니다.
Edge `outputs[].device_id`, `zone_id`도 중앙과 일치해야 합니다.
카메라 등록 외에 AI worker의 모델·계정·키 설정이 필요하며, 실제 RTSP 연결도 확인해야 합니다.

## 7. 현장 상세와 수동 제어

![현장 상세](screenshots/08_site_detail_overview.png)

개요에서 경보·기상·장비 수·Vision·센서 차트·CCTV·히터 상태를 확인합니다.
상세 탭에는 녹화, Control Logs, 장비 구성, 디지털 트윈, 에너지·정비 기능이 있습니다.

### 자동 제어 단계

| 단계 | 의미 |
|---|---|
| `off` | 위험 해소 또는 부하 제한 등으로 가열 정지 |
| `preheat` | 예보를 반영한 사전 예열 |
| `active` | 신뢰 Vision·센서·기후 위험도에 따른 가열 |
| `hold` | 잔류 위험과 재결빙을 고려한 가열 유지 |
| `safe_shutdown` | 과열·안전 래치·제어 통신 이상 등으로 안전정지 |

![제어 단계 예시](screenshots/15_site_detail_control_stage.png)

현재 물리 출력은 ON/OFF입니다. `preheat`·`hold`를 30%·20% 비례 출력으로 해석하지 않습니다.
제어 장비 통신이 끊기면 안전정지합니다. 안전 래치가 남아 있으면 냉각만 됐다고 즉시 재가동되지 않습니다.
화면의 요청 단계와 명령 수락을 실제 출력 성공으로 판단하지 말고 feedback·ACK를 확인합니다.

### 수동 제어

1. 슈퍼유저가 현장·장비·구역·현재 경보를 확인합니다.
2. 히터 ON/OFF를 선택합니다. UI 요청은 기본 60분이며 API 기간은 1~480분입니다.
3. 요청 성공 후 제어 이력과 명령 결과를 확인합니다.
4. 기간이 끝나면 자동 판단으로 복귀합니다.

수동 ON도 과열·센서 오류·안전 래치를 우회하지 않습니다.
Edge latch 해제는 현장 점검 후 로컬 승인 CLI로 수행합니다. 웹에서 임의 해제하지 않습니다.

Control Logs에는 이전/새 상태, 수동·자동 모드, 사유, 작업자, 시각이 기록됩니다.
권한이 없으면 조회·조작이 거부됩니다. 담당 관리자에게 확인을 요청합니다.

### Vision 상태 읽기

기본 모델은 `dry / wet / snow / ice`를 사용합니다. 확장 클래스는 배포 모델에 따라 다릅니다.
서버 기준 신뢰도(기본 75%) 미만은 `uncertain`입니다.
선택적 영상 품질 검사에서도 불확실로 바뀔 수 있습니다. 이때 센서·기상과 현장 영상을 대조합니다.
`지금 분석`은 분석 요청 기능이며 AI 패키지·가중치가 없는 백엔드에서는 실제 분석이 생략될 수 있습니다.
별도 AI worker의 상태와 최근 Vision 시간을 함께 확인합니다.

## 8. 영상 녹화·재생

1. 카메라의 라이브 영상 또는 스냅샷으로 대상이 맞는지 확인합니다.
2. `REC`로 녹화를 시작합니다.
3. 필요 시 `STOP`으로 종료합니다.
4. 녹화 영상 탭에서 카메라를 선택합니다.
5. 완료된 항목의 시각·길이·크기를 확인하고 재생합니다.
6. 재생 막대로 원하는 구간을 탐색합니다.

- 기본 최대 녹화시간은 60분이며 서버 `RECORDING_MAX_MINUTES` 설정에 따릅니다.
- 기본은 원본 스트림 저장이며 브라우저 호환이 필요한 H.265 등은 H.264 변환 경로를 사용합니다.
- 키프레임·연결 대기 때문에 시작 직후 일부 장면이 빠질 수 있습니다.
- 완료·검사·업로드가 끝난 녹화만 이력에 나타납니다. 실패 항목은 재생 목록에 나오지 않습니다.
- 녹화 중에는 서버 spool 디스크를 사용합니다. 장시간·동시 녹화는 여유 용량을 확인해야 합니다.
- 라이브 영상은 중계·인증·코덱·카메라 연결 상태에 영향을 받습니다.

## 9. 에너지·디지털 트윈·예지보전

### 에너지 관리

현장 피크 한도와 요금제를 설정하고 부하·전력 추세·추정 비용을 확인합니다.
피크 제한은 자동 구역을 우선순위에 따라 OFF하는 방식입니다. 출력을 미세 비례 감쇄하는 기능은 아닙니다.
수동 고정 부하도 한도 계산에 포함됩니다.
요금표·배출계수는 코드 기준 상수이며 최신 공식 요율을 자동 조회하지 않습니다.

### 디지털 트윈

도로 표면·발열 필름·지반 단면과 전기 계측 정보를 확인합니다.
수동 시뮬레이션의 전력 슬라이더는 가상 단면 시각화입니다. 실제 히터 제어와 구분합니다.
열지도 미래값·승온 시간·잔여수명은 모델 추정치입니다.

### 예지보전

| 점검 | 필요한 데이터와 의미 |
|---|---|
| 발열 균일도 | 가동 중 다중 온도 포인트의 편차·표준편차로 국부 이상 확인 |
| 저항 드리프트 | 전압·전류 및 과거 저항과 비교해 단락·누설·단선·접촉 이상 의심 |
| 승온 효율 | 난방 전력 대비 노면 온도 상승이 충분한지 확인 |
| 전기 열화·RUL | 전기·열 이력에서 열화 추세·잔여수명 추정 |

가열 구역과 `zone_thermal_samples`가 연결돼야 합니다. 표본·전압·전류·다중 온도값이 없으면 진단이 제한됩니다.
경보 발생 시 구역·시각·제어 상태를 기록하고 센서 배선·현장 상태를 확인합니다.
수명 추정만으로 장비 교체나 안전 판정을 확정하지 않습니다.

## 10. NOC와 운영일지

### NOC `/noc`

1. 미확인·미해결 경보와 심각도를 확인합니다.
2. 담당자가 경보를 확인(acknowledge)합니다.
3. 적절한 등록 사용자에게 담당을 할당합니다.
4. 현장 조치 후 해결 메모를 남겨 해결 처리합니다.
5. 과열·feedback 문제는 별도로 현장 안전 상태를 확인합니다.

경보 확인·해결은 물리 안전 래치 해제가 아닙니다.
미확인 5분·미해결 10분 경보는 단계적으로 격상될 수 있습니다.
설정된 채널이 켜져 있으면 이메일·SMS로 단계별 재발송합니다.

### 운영일지 `/logbook`

현장·날짜를 선택해 요약·융설 횟수·가동시간·장비 조치·문제·운영자 메모를 입력합니다.
같은 현장·날짜의 중복 일지는 거부됩니다.
주간 추천은 제어·이벤트·경보 이력을 조합한 초안이며 횟수·시간이 추정될 수 있습니다.
내용을 실제 조치와 대조한 뒤 저장합니다. 작성·수정과 삭제 권한은 다릅니다.

발송 수단은 서버 관리자가 SMTP·SMS webhook을 먼저 구성해야 합니다.

## 12. 일상 점검과 장애 대응

### 업무별 튜토리얼

- 관제 운영자: 대시보드에서 담당 현장 검색 → NOC 경보 확인·할당 → CCTV·센서 대조 → 조치 후 해결 메모·일지 저장.
- 현장 담당자: 현장 상세에서 장비·구역 확인 → 계측·feedback 점검 → 필요 시 현장 안전조치 → 담당 관리자에게 결과 보고.
- AI 담당자: AI 관제에서 위험도·결정 사유 검토 → 예보·원영상 대조 → 피드백 저장 → 모델·데이터 평가 절차 진행.
- 시스템 관리자: 서버 상태·디스크·키/인증서 만료 확인 → 설정·계정 검토 → 백업·복구 점검 결과 보존.

### 일일 점검

일일 업무 순서:

1. 로그인과 주요 화면 표시를 확인합니다.
2. NOC의 미확인·위험 경보를 먼저 처리합니다.
3. 담당 현장의 센서·기상·Vision·Edge heartbeat 시각을 확인합니다.
4. `safe_shutdown`, 명령 실패·ACK 지연, outbox 적체를 확인합니다.
5. CCTV·녹화 저장·디스크와 반복 정비 경보를 확인합니다.
6. 조치와 남은 문제를 운영일지에 남깁니다.

| 증상 | 우선 확인 |
|---|---|
| 로그인 실패 | 계정 활성·잠금·이메일·비밀번호·세션 만료. 기본 계정은 없음 |
| 대시보드 로딩·빈 데이터 | 재로그인, 조직·현장 필터, API 상태·실패 응답 |
| CCTV 없음 | RTSP/IP·현장 네트워크·중계·인증·코덱·worker 로그 |
| 녹화 이력 없음 | 종료 후 저장 대기, 카메라 연결, worker 실패 로그·spool 용량 |
| 지도 없음 | 현장 좌표·필터·외부 타일·Cesium 접근, 2D/3D 전환 |
| AI 결과 오래됨 | 카메라 처리 간격·AI heartbeat·모델 로드·계정·키·현장 범위 |
| 히터 명령 없음 | 권한·구역 매핑·Edge ID·키 만료·인터록·입력 신선도 |
| 온도 정상인데 안전정지 | 영속 latch·feedback·통신·냉각 유지조건, 현장 점검 여부 |
| 예지보전 없음 | 가열 구역과 실제 thermal-sample·전압/전류·과거 표본 |
| 이메일·SMS 없음 | 채널 활성·수신자 역할/조직·휴대폰·발송 등급·SMTP/webhook |

경보 발송은 기본 30초 주기로 처리하며 실패 채널은 경보 생성 후 15분까지 재시도합니다.
발송 설정 전에 생긴 오래된 경보가 모두 재발송되는 것은 아닙니다.

서버 관리자 점검 명령(저장소 루트):

```bash
central/scripts/ecoway.sh status
central/scripts/ecoway.sh logs worker
```

로컬 개발은 `./central/status.sh`를 사용합니다.
장애 대응·백업·인증서·복구 세부 절차는 `central/docs/OPERATIONS_RUNBOOK.md`를 따릅니다.
