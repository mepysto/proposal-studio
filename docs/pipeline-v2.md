# Proposal Studio v0.2 — 문제에서 의사결정으로 이어지는 제작 파이프라인

## 왜 제작 구조를 바꿨는가

v0.1은 파일을 생성하는 경로는 있었지만, 원문 발췌와 레이아웃 순환을 제안서 기획으로 취급했다. 페이지가 넘치지 않는다는 사실은 문제 정의가 옳거나 제안이 설득력 있다는 증거가 아니다. SmartFence 샘플은 가설울타리 정책 배경과 현장 확인 과제를 나열했지만, 시민·차량·유도원의 관계와 위험이 생기는 조건, 기존 대응으로 해결할 부분, AI가 추가로 보조할 부분이 분명하지 않았다.

v0.2의 목표는 **문제를 정의하고, 개입을 설명하고, 도입 결정을 검증 가능한 조건으로 만드는 것**이다. 이미지·도표는 그 논리를 독자가 이해하도록 돕는다. 근거 없는 숫자를 만들어 차트로 장식하지 않는다.

## 새 실행 경로

`자료 보존·추출 → 범위별 주장·근거 원장 → 의사결정/문제 브리프 → 원인·개입·검증 연결 → 기존 대안 비교 → 질문·답·근거 스토리보드 → 설명 목적별 시각자료 → PPTX/PDF/PNG → 기획 검사 + 렌더링 검사 → 내보내기`

### 1. 무엇을 결정받을 것인지 먼저 적는다

`planning.decision`은 결정 주체, 요청, 범위, 성공 판단, 범위 밖 항목을 가진다. ‘AI 시스템 도입’ 같은 솔루션 이름만으로는 문제를 정의하지 않는다. 마지막 장표에는 요청할 결정을 다시 표시한다.

### 2. 문제를 상황·사람·원인으로 나눈다

`planning.problem`에는 영향받는 사람, 구체적인 상황, 남는 과제, 결과, 기존 대응, 인과 메커니즘, 현장 근거 상태가 들어간다. 각 원인은 근거 주장 ID와 연결한다.

주장의 확실성(`user-provided`, `externally-verified`, `inference`, `assumption`)과 적용 범위(`general`, `local`, `project`)는 별개다. 일반 지침을 확인했다고 특정 천안 현장의 사고 빈도나 운영 공백을 확인한 것으로 승격할 수 없다. 확인하지 못한 지역 사실은 현장 조사 목록으로 남긴다.

### 3. 원인–개입–검증을 연결한다

`planning.interventions[]`는 `mechanismIds`와 `validationIds`를 참조한다. 어떤 문제에 개입하는지, 무엇을 만들고 어떤 결과를 확인할지 설명할 수 없는 기능은 기획 오류로 다룬다.

`planning.alternatives[]`에는 기존 대응인 baseline을 반드시 둔다. SmartFence에서는 동선·시야 개선, 유도원·CCTV 운영, AI 경고·기록 보조를 비교한다. 기존 대응에 문제가 있다고 확인되지 않았다면 부족하다고 단정하지 않는다. 제품을 팔기 위해 문제를 과장하지 않는다.

### 4. 한 장의 질문과 답을 먼저 정한다

`planning.story[]`의 각 beat:

- `question`: 청중이 알고 싶은 구체적인 질문
- `answer`: 그 장표가 전달할 주요 답
- `proofClaimIds`: 답을 지지하는 근거
- `visualPurpose`: 시각자료로 설명할 관계
- `limitation`: 독자가 확정 사실로 오인하면 안 되는 부분

원문 문단 순서나 장표 번호에 따라 레이아웃을 순환하지 않는다. 스토리의 설명 목적에 맞춰 시각 문법을 선택한다. 장표 제목·답·한계 문구를 기획에서 생성하고, 기획 해시를 저장한다. 기획이 바뀌거나 장표만 임의로 수정되어 서로 달라지면 재계획을 요구한다.

### 5. 사진과 도표의 역할을 나눈다

| 설명할 내용 | 구현한 표현 | 방지하려는 오해 |
|---|---|---|
| 의사결정의 대상·현장 맥락 | 개념 이미지와 편집 가능한 핵심 문구 | 실증 완료 현장 사진으로 오인 |
| 문제의 발생 조건 | 원인→영향 관계를 나눈 진단 구성 | 독립적인 요인을 무조건 직렬 인과로 연결 |
| 위치·동선·가림 | 영역·객체·경로·점검 위치를 가진 네이티브 공간 도식 | 추상 화살표를 실제 동선으로 오인 |
| 기존 대안과 도입 조건 | 동일 기준의 대안 비교 | AI 도입을 미리 결론내림 |
| 제안 장비와 역할 | 설치 개념도 + 기획 개입 ID에 연결한 번호 | 장비 이미지가 성능·감지범위의 증거처럼 보임 |
| 시스템과 사람의 책임 | 시스템/책임자/확인 기록 스윔레인 | 경고 송신 또는 ACK를 실제 조치로 오인 |
| 도입·확대의 판단 | 검증 질문/측정 방법/진행·중단 기준 | 측정하지 않은 성과나 목표를 실적으로 표현 |

표지와 설치 설명은 서로 다른 새 이미지를 사용했다. 설치 이미지의 번호는 원본 이미지의 정규화 좌표로 관리한다. 해당 이미지는 크롭하지 않고 비율을 유지해 삽입하므로 번호가 장비에서 벗어나지 않는다. 동선도와 스윔레인은 이미지가 아닌 편집 가능한 도형·텍스트다.

공간 데이터의 단위는 0–1 정규화 좌표이며 실제 거리를 뜻하지 않는다. actor 좌표는 중심점, barrier 좌표는 좌측 시작점과 너비를 뜻한다. 시야 가림 영역은 감지범위 측정 결과가 아니다.

## 검사와 수정 경로

`planningAudit`는 오류마다 `path`와 `returnTo`를 기록한다.

| 오류 | 돌아갈 단계 |
|---|---|
| 문제·결정 브리프 없음 | problem-framing |
| 근거 참조 누락, 검증 기록 누락, 일반→지역 도약 | research |
| baseline 없음, 개입의 원인/검증 연결 누락 | strategy |
| 해결책이 문제보다 먼저 나옴, 답 반복, 기획과 장표 불일치 | storyboard |
| 공간모델 누락, 잘못된 도식 형식·장비 앵커 | visual-design |

기획 오류를 렌더링으로 감추지 않는다. `qualityTarget: "proposal"`에서는 기획 오류가 있으면 PPTX 빌드 전에 차단한다. 배치·폰트·PDF 검사는 그 이후 별도로 실행한다. 수정 결과는 원본 기획에서 `plan`을 다시 실행해 갱신한다. 잘못된 사실을 자동으로 고쳐 사실로 확정하지 않는다.

검사 상태는 `draft-only`, `blocked`, `ready-for-human-review`로 나눈다. `ready-for-human-review`는 정의된 기획 계약이 연결되었다는 뜻이며, 사업 타당성·논리의 완전성·심미적 품질에 대한 전문가 최종 승인이 아니다. 자동 점수와 주관적 평가를 혼합하지 않는다.

## 실제 SmartFence 수정본

`examples/smartfence-v2.project.json`을 사용하는 7장:

1. 공사차량 출입구 보행안전 실증 — 이번 제안의 범위
2. 출입구에서 시민·공사차량 동선이 겹치는 문제 — 발생 조건과 현장 미확인 사항
3. 동선·시야·현장 통제 위치 — 물리적인 공간 관계
4. 기존 대안과 AI 보조의 조건 — 기존 안전조치 우선
5. 관측/경고/조치 기록의 설치 개념 — 장비와 개입을 연결
6. 시스템과 사람의 확인 책임 — ACK와 실제 조치를 분리
7. 검증 방법·중단 조건·다음 결정 — 후보 현장 공동 검토 요청

5장 안에 기존 대안과 검증 판단을 생략하지 않도록 두 장을 추가했다. 첫 시제품은 비교를 위해 그대로 보관했다.

문제의 일반 근거는 개발 중 실제 열어 확인한 HSE의 교통관리·시민 보호 지침과 CDC/NIOSH의 건설 장비 제한 시야 자료다. 출처·확인 구절·확인 시점·적용 한계는 `references/research/smartfence-evidence-2026-10-27.json`에 기록했다. 이는 한국 법규 해석, 천안 사고 통계, 현장 수요 조사 또는 제품 성능 실증을 뜻하지 않는다.

## 산출물과 실행

```bash
npm run demo
npm run studio -- audit --project smartfence-v2
npm run studio -- regenerate --project smartfence-v2 --slide risk
```

`projects/smartfence-v2/output/`에 PPTX/PDF/PNG와 함께 다음을 저장한다.

- `decision-brief.md`: 문제·원인·개입·대안·검증·각 장표의 질문/답/근거
- `planning-review.json`: 기획 계약 검사와 수정 경로
- `research-backlog.json`: 아직 수행하지 않은 현장 관찰·실험
- `qa.json`: 기획 상태와 실제 렌더링 검사

프로젝트 설정의 `planning`이 기획의 기준이다. 계획이 있는 프로젝트에서 `slides`의 문구만 바꾸면 동기화 오류로 차단한다. 이미지는 같은 ID의 기존 장표에서 보존한다. `run`은 분석·계획·제작·검수를 순서대로 재실행한다.

## 구현의 한계와 다음 연결

현재 기획 브리프는 검토해 작성한 구조화 입력이다. 원문만으로 전문 기획을 자동 작성하는 LLM, 실시간 검색, 이미지 생성 API는 프로그램에 연결하지 않았다. 개발 중 수행한 웹 조사와 내장 이미지 생성은 프로그램의 실행 능력과 구분한다.

다음 AI 연동도 텍스트를 곧바로 PPTX로 보내서는 안 된다. 역할별로 원인 후보·근거 범위·반대 대안·개입 가설·측정 계획을 생성하고, 동일한 스키마·검사·수정 경로를 통과한 결과만 다음 단계로 넘겨야 한다. 현재 여섯 역할의 출력은 제공 브리프 분석과 규칙 검사이며, 실제 LLM 호출을 수행한 것으로 표시하지 않는다.
