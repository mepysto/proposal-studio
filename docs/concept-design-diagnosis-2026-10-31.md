# 초기 기획을 디자인에 반영하기 위한 진단과 개선 설계

> 구현 전 진단 기록입니다. 이후 구현된 기능과 남은 범위는 [구현 계약](../skills/proposal-visual-storytelling/references/authored-compositions.md)과 [검증 기록](concept-design-implementation-2026-10-31.md)을 참고하세요.

2026-10-31. 요청 범위는 현재 제작 구조의 진단과 개선 방향 정리다. 이번에는 렌더러·QA·예제·로컬 프로젝트·PPTX/PDF를 바꾸지 않았다. 기획의 시각적 의도를 먼저 작성하도록 프로젝트 스킬을 보완했다. 아래의 신규 계약·모듈은 구현 제안이며 현재 지원 기능으로 표시하지 않는다.

## 결론

현재 엔진은 페이지가 무엇을 설명해야 하는지 비교적 상세히 보존하지만, 그 제안을 어떤 디자인 콘셉트와 장표 흐름으로 표현할지는 충분히 보존하지 못한다. 결과적으로 서로 다른 제안이 같은 에디토리얼 외곽 구조를 공유한다. 지난번 추가한 디자인 검수는 결과를 관찰하는 기능이며 이 생성 구조를 해결한 것은 아니다.

일관된 브랜드·가독성·근거·편집 가능성은 유지할 가치가 있다. 이를 모든 사업의 동일한 상단 띠·본문 높이·색 조합·박스 형식과 분리해야 한다. 같은 제안서 안에서도 설명 목적에 따라 장면, 비교, 증거, 운영, 결정 페이지의 무게와 시선 흐름이 달라질 수 있어야 한다.

| SafeSurface | 2026-10-29T00-07-26-039Z-9cd53e | 30 | 29 | 29 |
| SLT AI portfolio | 2026-10-30T03-53-33-314Z-a97035 | 23 | 22 | 22 |

제목 틀은 x=.64, y=.78, w=12.05인 32pt 제목, 강조 띠는 x=.64, y=1.78, w=12.04, h=.7인 primary-background를 뜻한다. 각 run의 config.json/elements.json을 대조했다. 총 80장 중 각각 76장에 같은 외곽 구조가 있다. 이 수치는 전문성 점수나 개선 목표가 아니다. 이 틀을 몇 퍼센트 이하로 줄이자는 뜻도 아니다.

세 프로젝트의 slide-03.png를 각각 원본 1600×900으로 열었다. 통합 서비스는 3개 제품 그룹, 재결빙은 4단계 상태, 정책 접점은 비교표로 본문 설명이 다르지만 모두 큰 제목→전폭 둥근 강조 띠→같은 본문 시작선 구조다. 청록/남색/옅은 바탕도 공유한다. 따라서 모든 본문이 동일하다는 주장은 부정확하지만, 외곽 구조와 시각 언어가 유사해 보인다는 사용자 관찰은 코드/출력 양쪽에서 뒷받침된다. 이번에 80장 전체를 눈으로 다시 검수한 것은 아니다.

## 필요한 초기 설계 산출물

첫째, 제안별 디자인 브리프를 만든다. 기획의 핵심 아이디어 한 문장, 청중에게 이해시킬 관계, 그 관계가 보이는 방식, 브랜드의 고정 요소, 참고자료의 채택/비채택, 피해야 할 표현을 함께 쓴다. ‘공공기관용·깔끔하게·청록색’만으로는 부족하다.

둘째, 콘셉트를 실제 장표 결정으로 번역한다. 예를 들어 ‘감지보다 감지 이후의 대응 연결이 가치’라면 실제 현장·행동 주체·대응 경로를 연결하고, 감지와 확인된 물리 동작을 분리한다. 모든 페이지를 회로 배경이나 화살표로 장식하는 것은 콘셉트 구현이 아니다.

셋째, 전체 흐름의 작은 설계도를 만든다. 각 페이지의 역할(상황 인지/설명/근거/판단), 주 시각물, 크기 관계, 시선의 시작/이동, 앞뒤 페이지와의 연결을 기록한다. 중요 페이지에는 충분한 면적과 호흡을 주고 상세 비교/운영에는 반복 축을 허용한다.

넷째, 대표 페이지 몇 장으로 방향을 확인한다. 사업 이해·차별점·근거/결정을 대표하는 서로 다른 페이지가 적절하다. 이 단계에서 콘셉트가 실제로 보이지 않으면 전체 양산 전에 바꾼다. 필요한 경우 서로 다른 공간 구성을 비교하되 색상만 다른 안이나 같은 틀의 변주는 대안으로 보지 않는다. 모든 작업에 고정된 대안 개수나 별도의 사용자 승인 절차를 강제하지 않는다.

## 같은 브랜드 안에서 다른 아이디어를 표현하는 예

아래는 디자인 제안이며 새 사실·측정 결과나 확정된 고객 요구가 아니다.

| 제안 | 기획을 시각적으로 표현할 방향 | 대표 구도 | 유지할 사실 한계 |
|---|---|---|---|
| SmartFence | 실제 출입구에서 감지→안내→유도원 통제→확인의 연결 | 큰 현장 장면에 행동 경로·수신자를 직접 배치, 시스템 페이지는 현장/장비/관제 경계와 장애 경로 | 미검출은 통행 허가가 아니며, ACK는 물리 완료가 아님 |
| SafeSurface | 같은 접근로가 시간과 환경에 따라 다시 위험해지는 과정 | 같은 지점의 조건 변화 대조, 표면/보행 경로와 운영 시점의 연결 | 상태 변화 설명용 개념 장면과 실제 온도·성능 측정을 구분 |
| SLT AI portfolio | 도시의 여러 현장을 묶는 서비스 관계와 공통 대응 체계 | 적용 현장들의 관계를 먼저 조망하고, 개별 사용 사례로 확대 | 실제 미확인 연동·성능·예산을 확정하지 않음 |

아이디어가 위와 다르게 정의되면 다른 표현을 선택한다. 사업 이름별로 ‘현장형/시간형/도시형’ 템플릿을 영구 지정하면 같은 문제가 반복된다.

## 구현 순서와 완료 조건

1. **콘셉트 브리프와 보존 경로**: 선택적 designDirection와 페이지별 compositionBrief를 설계하고 스키마→story→compiled slide→run snapshot→검수까지 전달한다. 정확한 필드 구조는 구현 때 결정한다. 현재 Zod 입력에 지원하지 않는 키만 추가하면 기본 파싱에서 사라질 수 있으므로, 원본에 임의 키를 넣고 구현됐다고 주장하지 않는다. 레거시 입력은 기존 경로를 유지한다.
2. **실제 디자인 설정 적용**: 공통 T를 프로젝트별 resolved tokens로 바꾸고 ctx/kit에 전달한다. 레거시 토큰을 기본으로 유지한다. 색뿐 아니라 메시지 처리 방식, 콘텐츠 영역, 시각물 비중, 캡션/주석 방식과 텍스트 위계를 포함한다. 모듈 전역 T를 실행 중 덮어쓰는 방식은 동시 제작 오염을 일으킬 수 있어 피한다.
3. **정보 구조와 구도 분리**: visualPlan은 무엇을 입증/설명하는지, compositionBrief는 어디에 어떤 크기로 어떻게 읽는지를 맡는다. 지도/네이티브 차트/현장 장면/상태도/비교표는 계속 의미 구조를 보존한다. unsupported composition은 조용히 공통 틀로 대체하지 않고 명시적 미지원/저술 필요 상태로 보고한다.
4. **QA를 선언한 설계와 대조**: 브랜드·가독성·근거·위계·크롭·연결선 검사는 보존한다. 현재의 둥근 강조와 큰 핵심 문구도 유지하되 페이지의 해당 관계에 가까운 배치로 확장할 수 있어야 한다. x=.64 전역 판정은 legacy 기본 또는 저술된 페이지 anchor 판정으로 바꾼다. 시각 정책을 끄거나 검사 임계값을 낮추지 않는다.
5. **대표 구도 구현 후 출력 비교**: 같은 정보 구조를 서로 다른 저술 의도에 따라 실질적으로 다른 시각물 비중/시선 흐름으로 구성할 수 있는지 확인한다. ‘설정 값이 존재함’ 테스트보다 렌더된 요소 위치/크기/내용, 편집 가능성, PDF/PNG에서의 실제 읽힘을 확인한다. 전체 5/7/27장 회귀 검증과 영향 페이지의 원본 크기 검토를 수행한다.

이 순서는 테마 스위치나 플러그인 추가보다 먼저다. 현재 도구는 표현 자산 제작에 충분하며 입력과 렌더러 사이의 설계 전달 경로가 우선 결손이다. 이번 진단을 근거로 새 플러그인/의존성을 설치하지 않았다.

## 이번 반영과 남은 일

반영: 프로젝트 스킬에서 초기 콘셉트의 시각 번역을 명시하고 별도 저술 가이드를 연결했다. 앞으로 기획 시 기존 사례의 청록/제목/띠/박스를 자동 출발점으로 삼지 않도록 했다.

미구현: 신규 스키마, 디자인 토큰 해석기, 구도 배치기, 페이지별 QA 계약, 대표 시안의 실제 렌더. 따라서 현 엔진이 이제 콘셉트 기반으로 자동 제작한다고 말할 수 없다. 기존 27장과 다른 프로젝트 출력은 그대로다. 이번 변경은 문서/스킬이며 타입/렌더 동작 변경은 없다.
